# Task 3 interpretations

- T3.md was absent; the current user prompt is copied into it with provenance. Existing baseline approval remains applicable.
- All six customer fields are mandatory by default, including explicit evidence (a customer statement is allowed). Missing data produces a persistent draft and a field-specific question, never a final ticket. Structured updates complete drafts through the ticket API. An unresolved RAG refusal/ambiguity, support escalation, configured explicit handoff phrase or customer-supplied unresolved flag automatically starts drafts per detected request. Language clarification alone is not an unresolved policy failure. An explicit unresolved flag does not require a RAG failure.
- Customer identity/contact are explicitly supplied, never inferred from API keys or generated summaries. Ownership is derived from the authenticated key independently of those fields. Drafts reuse actual session summaries and latest request-specific order/product entities. Corrections may update drafts, never silently rewrite existing tickets.
- Severity and impact are operational inputs with documented configurable defaults, not invented customer facts. SLA targets are selected by severity, avoiding a circular priority/SLA calculation. Waiting time is elapsed business time since creation, including assigned time.
- Similarity is deterministic token Jaccard after configured stop-word removal. Duplicates require the same owner, customer, order, product, and configured issue family (or exact normalized issue when unknown). Negation and digit-bearing tokens must match. Related issues share owner/customer/order/product and a configured family. Unmapped issues group only by exact issue; unrelated requests remain separate even in one session. A duplicate preserves its earliest final creation timestamp, all request/evidence/contact records, and the highest configured severity, impact and sentiment component; it cannot restart the SLA or downgrade urgency.
- Business intervals are half-open, same-day hours in the configured timezone. Ticket SLA starts at creation; off-hours consume zero. Before opening, tickets wait for that day's opening; after closing, the next working opening. T5's existing next-working-date presentation is preserved.
- Warning occurs at >=75%; breach at >=100%. Durable events fire once per ticket and condition; a changed target recomputes every open ticket on the next tick without resetting its creation time. A previously breached ticket retains escalation history even if a relaxed rule clears its current breach state.
- Empty production agent roster is intentional. No synthetic available agents are shipped. Queue age escalation uses business minutes and a configured destination. Events and queues are durable local records; no external helpdesk or notification transport is configured.
